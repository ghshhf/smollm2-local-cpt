# 云端训练规范（集各家所长版）
> 用户决策（2026-10-14）：**整体训练上云，本地不再承担训练。** 本地只做方法学探针、数据准备、验收评测。
> 本文件把开源社区验证过的做法固化成我们的执行标准——凡是社区已有定论的，一律照抄，不自创。

## 零、分工

| 环节 | 谁做 | 理由 |
|---|---|---|
| 预训练长跑 | **云端**（node1 64 核 / GPU 100h 储备） | 本机 12 核，实测 595 tok/s，物理上训不出能力 |

## 一、吞吐：先把 CPU 喂饱（本次最大修正）

**社区共识**：小模型 batch **0.5M~1M token**（MiniMind 明确说"小模型 batch 不需要太大"是相对大模型而言，不是指绝对小）。

**我们原来的错**：`train_remote_v4.py` 硬编码 `batch_size=1, max_len=512, accum=8`
⇒ **每步仅 4096 token**，比社区建议低 **2~3 个数量级**。
矩阵乘是 (1×512)×(576×576)，太小 ⇒ 64 核跑出 18.7 s/步 = **4.4 GFLOP/s/核，约峰值 5~10%**。

**诊断证据**：本机 10 线程 `bs=8` 反而跑出 **7.3 GFLOP/s/线程**，比 node1 单核还高。差异就是 batch size。

**修正**（已写入脚本）：
```
--batch 16 --accum 2 --max_len 512    => 16,384 token/步（原 4,096）
```
脚本已加 `[warn]`：每步 <8192 token 时自动告警。

> ⚠️ 算力受限时**宁可加大 batch 减少步数，也不要小 batch 多步**。
> 我们离"临界 batch"还差得远，加大 batch 只会更快、更稳，不会伤收敛。

## 二、数据：shard + manifest + seed（照抄社区）

社区标准做法，解决"续训不可复现"：

- 每片 **不可变**，落盘后不再改
- **manifest** 记录：片名 / token 数 / 域 / 内容 hash / tokenizer hash / shuffle seed
- ⇒ **训练顺序 = manifest + seed + step 的纯函数**

**收益**：① 可精确续训 ② 出现 loss 尖峰时能**定位并跳过某段坏数据** ③ 换 tokenizer 时能立刻发现片不匹配。
**当前缺口**：我们现在只靠 ckpt 续训，数据顺序不可重放 —— 下一步补上。

## 三、配比与 epoch 上限

- **每域 epoch 上限 ≈ 4**（社区实测：超了收益急剧下降，剩下全是死记硬背）
  ⇒ 已据此把 owner_corpus 的 upsample 从 **50× 砍到 4×**（见 `data-plan-0.4B.md`）
- **配比搜索用小代理**：中关村学院 ZGCM1 用 **0.3B 代理模型在 30B token 上搜配比**，再大预算复用，
  评价是"穷队友好"。**我们今天跑的 20M 代理试验就是同构做法，社区已背书。**
  消融成本 <总预算 10%，回报是数倍。

---

## 四、课程学习（ZGCM1 的发现）

- 按**词汇复杂度从低到高排序**，确实有效
- **但代码和数学要单独拎出来交错训练** —— 复杂度排序反映不了推理难度
  （一段 LaTeX 公式的词汇复杂度很低，推理难度却很高）
- **上下文渐进**：16K → 64K → 256K 分阶段，比直接上 256K 的 loss 更低
  ⇒ 与我们"逐级夯实"同构，也印证 0.1B 一级级往上是对的

## 五、超参（社区收敛值，我们已基本对齐）

| 项 | 社区值 | 我们的值 | 状态 |
|---|---|---|---|
| 优化器 | AdamW β=(0.9, 0.95) | 同 | ✅ |
| 学习率 | 3e-4（从零）/ 1e-5~3e-5（增量） | 3e-4 | ✅ |
| 调度 | WSD 或余弦 | WSD + 余弦 | ✅ |
| 权重衰减 | 0.1 | 0.01 | ⚠️ 偏小，可试 0.1 |
| 梯度裁剪 | **1.0 必须开** | 1.0 | ✅ |
| 序列长度 | 512~1024（小模型别太长） | 512 | ✅ |
| 批大小 | 0.5M~1M token | **16K（已修正，仍偏小）** | 🔴 继续往大调 |
| 精度 | bf16（A100+） | fp32（CPU 限制） | ⚠️ CPU 无 bf16，接受 |

> 社区还记了个"活人运维坑"：恢复训练后吞吐从 585 慢慢掉到 554，是显存碎片化，
> 每 100 次迭代清一次 allocator cache + GC 就恢复。**这类坑没踩过写不出来** ——
> 我们的对应版本是 ECS 同名文件锁（见 `REMOTE-OPS.md`）。

## 六、GPU 100h 的动用条件

用户已定"战略储备，不烧在 CPU 能干的活上"。具体触发条件：

| 触发 | 说明 |
|---|---|
| **0.3B 扩容重训** | 350M 在 CPU 上是 214M 的 1.6× 成本，R6 级别语料会拖到数十小时 |
| **0.4B 加词表后的重训段** | embedding/lm_head 全换，需要较大算力重新稳定 |
| **0.5B BitNet 原生 QAT 从头训** | 1-bit QAT 必须从头，GPU 上虽然不为 1-bit 优化，但算力绝对值大 |
| CPU 单阶段 ETA > 24h | 兜底条件 |

⚠️ AMD ROCm 非 CUDA：迁移只需改 device 放置（ROCm 下 torch device="cuda" 自动映射 HIP）；
agent + 数据通路需在新实例重部署。
