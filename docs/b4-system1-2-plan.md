# B4 研究计划：350M~500M 小模型的 System 1/2 混合推理（按需计算分配）

> 用途：自包含研究 brief，可直接整篇粘贴给强模型（Claude / GPT-class / ClawsGO 等）请其按"四个 Gate"逐项交付可跑方案与 PyTorch 骨架。
> 定位：本计划是 `docs/research-questions-for-experts.md` 中 B4 条目的详细版。核心问题 = 如何让 350M~500M 参数的小模型具备**按需分配计算量**的 System 2 深度推理能力，同时把 **CPU 推理成本控制在可用范围**。

> **v2（2026-10-15 晚）**：强模型（ChatGPT）审查意见已并入——四机制计算闭环、训练五阶段 A–E、优先级修订（先递归→再路由→最后停止）、停止头独立、KV cache 修正。见 §2/§4/§5/§7/§10。\n> **v3（2026-10-15 深夜）**：强模型工程伪代码（四机制）+ 推荐的最小文件拆分 + 消融矩阵 A–E 已并入（§11）。两个代码设计前必定的问题已按本项目实情作答（§11.4）：基础模型 = 自有 SmolLM2 续训权重（复用权重+少量新模块）；框架 = PyTorch + HuggingFace Transformers。落地脚手架见 `b4/`。

## 0. 一句话定位
让小模型**识别哪些问题值得多花计算量，并且确实从额外计算中获得收益**——而不是每次都输出更长的思维链。

## 1. 核心目标与关键区分
- **核心目标**：相同质量下降低成本，或在可接受的额外成本下提高正确率。
- **必须区分的两个概念**：
  - **输出思维链 = 生成更多文本**（更多 token）。
  - **System 2 = 执行额外的、能够改善答案的计算**（潜在循环，不一定要解码成文本）。
  - **前者并不自动带来后者。** 这是整个课题最容易踩的坑：把"吐了长 CoT"误当成"做了有效推理"。

## 2. 三模块分解（可独立验证）
课题不押注单一架构，拆成三个互相解耦、可分别做消融的模块：

| 模块 | 职责 | 独立验证点 |
|------|------|-----------|
| **① 路由决策 (router)** | 判断问题难度/预期收益，决定走 System 1 还是 System 2、循环几次 | 路由是否有预测价值（Gate 1） |
| **② 迭代推理 (iterative reasoning)** | 共享的潜在循环模块，执行额外计算以改善答案（非 CoT 文本） | 额外计算是否有用（Gate 2） |
| **③ 计算预算控制 (compute budget control)** | 验证与停止控制：答案质量、剩余预算、停止条件、必要时回退 | 路由是否优于固定预算（Gate 3）/ CPU 是否获益（Gate 4） |

- 模块①提出动作，模块③对动作做预算约束（见下方 `budget_constrained_policy`）。
- 模块②在第一版里**固定 2 次和 4 次迭代**，不先做自适应停止，避免同时发明三套机制（v2 优先级修订与此一致，见 §7）。
- **v2 四机制计算闭环**：① 输入与轻量路由器（提取问题特征/难度/不确定性/任务类型）→ System 1 直答（低难度走常规前向，用蒸馏直答能力）或 System 2 内部计算（高难度进**潜在状态递归循环**，逐步更新内部表示）→ ② **自适应停止控制器**（判断是否已有足够证据形成可靠答案，不足则继续计算）→ ③ **最终答案解码器**（输出答案、置信度估计与必要的验证结果）。训练时加 答案监督+难度监督+停止监督；推理时由路由器和停止控制器共同决定计算预算。**三者不能混成一个简单的"置信度阈值"。** COCONUT 已验证连续隐状态反馈可行，但原论文用**固定步数**——自适应停止需额外设计与训练。

## 3. 架构方向（基线，非最优）
```
System 1：快速回答
  350M~500M 主干模型 · 单次常规解码
        │
  轻量路由器（置信度校准 + 任务难度 + 预期收益）
        ├── 简单任务 ──▶ 直接输出答案，避免额外推理开销
        └── 困难任务 ──▶ 进入共享循环推理模块，允许多步计算
                              │
                      验证与停止控制
        （答案质量 / 剩余预算 / 停止条件 / 必要时回退）
```
- **System 1**：主干模型单次常规解码，零额外开销。常识、填空、简单指令走这。
- **共享循环推理模块（System 2）**：在连续隐状态里多步"想"（COCONUT 式把上一步隐状态当下一步输入 embedding 喂回，不解码成 token），最后才解码答案。难题才花这笔钱。
- **轻量路由器**：必须近乎零成本，否则省的算全贴回路由器。

### 3.1 路由器具体草图（模块①，用户给出）
```python
# h0: 主干模型首层或浅层的 pooled hidden state
# stats: 可选的低成本不确定性特征

x = concat(
    layer_norm(h0),
    stats
)

z = gelu(linear(x, 128))
logits = linear(z, 3)

# 三类动作
# 0: DIRECT
# 1: THINK_2
# 2: THINK_4
action = budget_constrained_policy(logits)
```
- 输入：主干**首层/浅层 pooled hidden state** + 可选廉价不确定性特征（如预测熵、top-k 置信度）。
- 结构：LN → GELU(Linear 128) → Linear 3（三类动作）。参数量极小，对 350M~500M 主干可忽略。
- 输出经 `budget_constrained_policy` 做预算约束后落地为动作（与模块③耦合）。
- **v2**：候选预算扩为 **0/1/2/4/8 递归步**；"何时退出"从路由器拆出，交给独立**停止头（小型二分类器：继续计算 or 退出）**——它学的是"继续计算能否改善结果"，路由学的是"该不该开始"。

## 4. 训练数据怎么造：答案蒸馏为主，少量显性思维冷启动
**关键判断**：System 2 不一定需要把显性思维链作为主要训练目标。若采用潜在循环计算，模型要学会的是**如何利用额外计算改善答案**，而非单纯模仿长篇解释。

**v2 定稿：五个训练阶段（借鉴 COCONUT 课程式训练——不能指望只加递归结构就自动获得推理能力；直接从最终潜在推理阶段开始训，效果可能不如逐步引入）**

- **阶段 A：直答基线蒸馏（必做）**——用大模型生成的高质量「问题 → 正确答案」蒸馏，先训稳定 System 1。覆盖数学、逻辑、常识、代码、指令跟随，**保留独立验证集**。
- **阶段 B：潜在递归训练**——先在有明确答案的数学/逻辑任务上训。可用大模型的可验证解题步骤作训练课程，但最终目标是让潜在状态帮助预测正确答案，**不是要求把每个步骤翻译成文字**（显性推理文本只作辅助监督，不应预设它一定能改善潜在循环模块）。
- **阶段 C：自适应停止训练 + 离线标签**——对同一道题测不同递归步数，记录正确率、延迟、计算量；把「继续计算是否能改善结果」作为停止控制器的训练信号。同时产出路由标签 $a^*=\arg\max_a[U(a)-\beta C(a)]$，并收集「多算变好」/「多算没用」两类样本。
- **阶段 D：混合路由训练**——把简单题、困难题、模型容易误判的题混合训练；路由器学**何时调用 System 2**，而不是只学题目表面长度。
- **阶段 E：联合微调**——小学习率联合优化答案质量、路由准确性、计算成本；**每次修改都与直答基线及固定步数递归模型对照**。

## 5. 损失函数（第一版组合损失）
$$
\mathcal L = \mathcal L_{\mathrm{answer}} + \lambda_r \mathcal L_{\mathrm{router}} + \lambda_s \mathcal L_{\mathrm{stop}} + \lambda_c \mathcal L_{\mathrm{cost}}
$$
- $\mathcal L_{\mathrm{answer}}$：答案 token 的交叉熵。
- $\mathcal L_{\mathrm{router}}$：路由损失，标签来自阶段 C 离线实验（见下）。
- $\mathcal L_{\mathrm{stop}}$（v2 新增）：停止头「继续计算 vs 退出」的二分类监督。
- $\mathcal L_{\mathrm{cost}}$（v2 新增）：计算成本惩罚——同时优化准确率和效率。
- $\mathcal L_{\mathrm{consistency}}$（v2 降为可选辅助）：约束循环状态 / 多次计算后的答案行为，避免额外迭代导致退化。
- ⚠️ **答案一致不代表答案正确。** 一致性损失只能作辅助项，不能替代正确答案监督。

### 路由标签的离线生成
设 $a$ 是动作（DIRECT / THINK_2 / THINK_4），$U(a)$ 是任务效用，$C(a)$ 是实际计算成本，则选择：
$$
a^* = \arg\max_a \big[ U(a) - \beta\, C(a) \big]
$$
- **$U(a)$ 应由任务正确率、错误严重性和必要的校准指标决定，而不是直接采用教师模型的自信程度。**
- 路由标签通过离线实验（阶段 C）生成，测试集不得参与路由器训练；用独立验证集校准阈值。
- **v2：路由器不能只优化分类准确率，要优化实际收益**：
$$
J = \mathbb{E}[\text{答案损失}] + \lambda\,\mathbb{E}[\text{计算成本}]
$$
$\lambda$ 控制愿意为提高准确率支付多少计算开销。
- **v2：模型自报置信度 ≠ 真实正确率。** 停止控制器必须用**校准后**的信号，并在独立验证集上检查不同置信度区间的实际准确率。
- **v2 失败模式对照**：漏触发（以为简单、直接答却答错）vs 过度计算（对普通问候启动 8 步潜在推理）——路由器与停止头是整套架构**最容易失败、最值得优先研究**的部分。

## 6. CPU 实测账：三档到底能快多少？（必须实测，不能仅凭参数量推算）
已有研究表明：计算量下降不必然转化为同比例的墙钟时间下降；官方 `llama-bench` 也明确区分 prompt 处理与 token 生成速度。

### 6.1 三种方案比较定义
| 方案 | 推理方式 | 主要成本 |
|------|----------|----------|
| **A：全直接答** | 不循环、不强制长思维链 | 基线延迟 |
| **B：全吐 CoT** | 每题都生成显性推理文本 | 增加生成 token，且答案未必更准 |
| **C：混合模式** | 路由器决定直接答或循环推理 | 路由开销 + 部分样本额外计算 |

⚠️ 若 C 使用潜在循环模块，它**不是 B 的简单缩短版**。两者应分别报告，否则无法区分收益来自额外计算还是文本生成策略。

### 6.2 先做一个可复现的 CPU 基准
固定**同一份 350M~500M 主干、同一量化精度、同一 tokenizer、同一组测试题**，记录：
- 首 token 延迟（TTFT）、端到端延迟的中位数与 P95。
- prompt tokens/s、生成 tokens/s、总生成 token 数。
- 正确率、数学与代码任务准确率、格式遵循率。
- 路由器调用耗时、循环次数分布、平均每题计算量。
- 峰值内存、CPU 型号、线程数、运行库版本。

### 6.3 计算器示例（⚠️ 以下默认数值仅为演示假设，非任何模型实测；改成你的实测数据即可）
| 指标 | 全直接答(A) | 全吐CoT(B) | 混合(C) |
|------|-----------|-----------|---------|
| 端到端延迟 | 500 ms | 1400 ms | 650 ms |
| 正确率 | 60% | 68% | 66% |
| 速度比(相对A) | 1.00× | 0.36× | 0.77× |
| 正确率差(pp) | — | +8 | +6 |

（速度比 <1× 代表更慢。）

### 6.4 加速比应该怎么报告
以直接答为基线：
$$
S_{\mathrm{mix}} = \frac{T_{\mathrm{direct}}}{T_{\mathrm{mix}}}
$$
- **精度损失用百分点（pp），不要混淆成相对百分比。** 例：正确率 80%→76%，损失 = 4 个百分点（相对下降 5%）。
- **混合模式不一定比直接答更快。** 它的价值可能是用较小的平均延迟换取更高准确率。要证明它更优，需同时展示**质量—延迟曲线**，而非只报一个加速倍数。

## 7. 实验顺序与通过标准（四个 Gate）
先验证可行性，再投入更重的训练。

**⚠️ v2 优先级修订（强模型审查）：改为「先递归 → 再路由 → 最后停止」，不要一开始同时调试多个不稳定机制。**
1. **第一优先：直答蒸馏 + 固定步数潜在递归**——先证明同一模型规模下潜在递归确实能提高困难任务准确率（≈Gate 2），否则没必要叠加自适应控制。
2. **第二优先：加入路由器**——先比较固定预算与简单难度路由（Gate 1/3），明确额外计算收益是否覆盖成本。
3. **第三优先：学习停止机制**——在「递归步数—性能」关系已知后，再训模型自行决定何时停止。
总路线：**先证明"潜在递归有用" → 再证明"自适应路由能以更少计算获得相近或更高准确率" → 最后联合训练。**

- **Gate 1 — 路由是否有预测价值？**
  固定同一主干，比较 prompt 统计、首层隐藏状态、浅层隐藏状态与组合特征。用独立验证集校准阈值，测试集不得参与路由器训练。
- **Gate 2 — 额外计算是否有用？**
  比较循环 1/2/4 次，确认至少一类困难任务获得**可重复的准确率提升**，同时记录延迟与内存。
- **Gate 3 — 路由是否优于固定预算？**
  混合模式必须与 全直接答 / 全循环 2 次 / 全循环 4 次 比较，避免只与一个较弱基线比较。
- **Gate 4 — CPU 是否真正获益？**
  在目标 CPU、相同量化精度、相同任务集上测端到端延迟。建议把 **P95 延迟、任务准确率、平均计算成本** 设为联合验收指标。

参考基线可用官方 [llama.cpp 基准工具](https://github.com/ggml-org/llama.cpp/tree/master/tools/llama-bench) 测常规推理性能；但要测自定义循环层和 gating head，还需在模型执行路径中增加计时与循环次数统计。

### 7.1 v2 增补：至少监测四个指标
- **答案准确率**：System 2 是否真正提高难题表现。
- **路由召回率**：需要深度推理的问题有多少被成功触发。
- **平均计算成本**：每个问题平均执行多少递归步。
- **选择性风险**：模型选择直接回答时，错误率有多高。

### 7.2 v2 增补：对潜在状态的硬质疑测试
潜在状态本身不一定等于可靠的推理过程——近期研究已对「潜在推理是否真正编码了关键推理信息」提出质疑。因此必须测：**分布外泛化、反事实干扰、数据捷径**，不能只看训练集或单一基准分数。

## 8. 最终建议（第一版先做什么）
第一版**不要同时发明**路由器、潜在思维机制和自适应停止算法。先做：
1. 现有 350M~500M 模型作为 **System 1**。
2. 一个小型、可校准的 **gating head**（见 3.1 草图）。
3. 一个**共享循环模块**，固定 2 次和 4 次迭代。
4. 以**答案蒸馏为主、少量可验证显性推理为辅**的训练数据（阶段 A→B→C）。
5. 同一测试集上的**三档 CPU 实测与质量—延迟对照**（第 6 节）。

**最重要的判据不是"模型看起来更会思考"，而是：在相同质量下是否降低成本，或者在可接受的额外成本下是否提高正确率。如果这两个条件都不成立，就应该先改训练目标或路由信号，而不是继续堆叠架构复杂度。**

按上述四个 Gate 逐项给可跑方案与 PyTorch 骨架，至少覆盖：
1. **路由器**：离线标签生成流程（$a^*=\arg\max_a[U(a)-\beta C(a)]$，U 来自正确率/错误严重性/校准，非教师自信）+ 在 350M~500M 上的 gating head 实现（含 3.1 草图的张量形状）。
2. **潜在循环模块（System 2）**：在 350M~500M 上的架构选择（连续思维 head / ACT / 循环层），以及对应的训练数据构造（阶段 A/B/C 落地为数据配方）。
3. **CPU 基准**：同一主干上三档（A/B/C）的实测方案（llama-bench + 自定义计时与循环统计），产出质量—延迟曲线与 P95 联合验收指标。
4. 最好给一个**能在 0.3B 上做最小消融的实验脚本**（v2 顺序：固定步数递归先行），让我们本地（CPU 为主）即可验证可行性，再决定 0.4B/0.5B 是否重训。
5. **v2 追加交付**（对应强模型下一步承诺的"可审查技术设计 brief"）：路由器结构规定、潜在递归伪代码、停止头训练信号定义、训练数据格式（阶段 D 混合难度样本）、消融实验矩阵（部分层 vs 全层递归｜固定步数 vs 自适应停止｜λ/β 扫描）。

## 10. v2 增补：工程细节、MVP 表与架构选择（强模型审查）
1. **不要默认整个 Transformer 都重复运行。** 先测「共享全部层」vs「只重复部分层」：部分层递归更容易控制推理成本，但可能损失计算深度。
2. **不要默认潜在推理不增加 KV cache。** COCONUT 只是避免了每个潜在思维步的词表投影；递归仍需前向计算，可能产生额外缓存与激活开销，取决于层复用方式、缓存状态与注意力处理。（⚠️ 此条修正本计划早前"不膨胀 KV cache"的乐观说法——那是实现依赖的，不是自动免费。）
3. **架构选择提前确认**：基础模型**已预训练完成 → 优先复用现有权重、少量新增模块**（我们的 0.3B/0.4B 续训链路正属此列）；若从头预训练，递归结构、位置编码、缓存机制、训练课程都应在更早阶段纳入设计。

### v2 最小可行设计（MVP）
| 模块 | 第一版实现 | 目的 |
|------|-----------|------|
| 基础模型 | 350M~500M 现有 Transformer | 保留语言理解和生成能力 |
| 路由器 | 轻量 MLP，读取问题末端隐状态及少量统计特征 | 预测是否需要深度计算 |
| 潜在推理 | 复用部分 Transformer 层，将归一化后的隐状态作为下一步输入 embedding | 在连续空间迭代 |
| 计算预算 | 0、1、2、4、8 个递归步数的候选预算 | 控制计算成本 |
| 停止头 | 小型二分类器，预测继续计算还是退出 | 学习自适应计算 |
| 训练目标 | 最终答案损失 + 路由损失 + 停止损失 + 计算成本惩罚 | 同时优化准确率和效率 |

## 11. v3 增补：强模型工程伪代码 + 落地文件（2026-10-15 深夜）

### 11.1 四机制伪代码（强模型给出，已并入；完整可运行版见 `b4/`）
- **统一入口 `solve()`**：`encode` → `route_score` → System1 直答 / System2 潜在递归（`MAX_STEPS` 循环，每步算 `confidence`+`stability`，`should_stop` 退出）→ `decode_answer`。
- **`LatentReasoner`**：复用基础模型**部分 Transformer 层**，`x=state_norm(state); update=shared_layers(x,context); next_state=state+update`。⚠️ 本项目用 HF `LlamaDecoderLayer`，其**内部已含 input_layernorm + 残差**，故 wrapper 直接返回 layer 输出即可（见 `b4/latent_reasoner.py`）。
- **`adaptive_reasoning`**：循环里 `stop_prob=stop_head(state)`，`step<MIN_STEPS` 不停止，`>=STOP_THRESHOLD` 退出，返回 `(答案, 步数)`。
- **`route_question` / `solve_with_router`**：router 读 hidden，`>=DIRECT_THRESHOLD` 走 SYSTEM_1，否则 SYSTEM_2。
- **`train_direct_model`**：只对目标答案 token 算 LM loss（teacher forcing + loss 掩码）。
- **`train_hybrid_model`**：并行算 `direct_logits` / `latent_logits`，组合 `total = direct_loss + latent_loss + λr·route_loss + λc·compute_loss`。⚠️ 路由硬开关无梯度 → 第一版**先分训两路径+router，再联合微调**；`routing_supervision` 不得直接拿两个 logits 当正确性标签。
- **强模型硬警示（已收入）**：① 不能把"连续两步隐状态相似"当答案正确证据（可能稳定停在错误状态）；② `latent_state` 是单向量而解码器要一串 token 隐状态 → 需投影层或状态→序列接口（本脚手架用"末位隐状态过剩余层+lm_head"解码首 token，完整答案走正常 generate）；③ 多算步数的浮点/KV 开销取决于层复用方式，不是自动免费。

### 11.3 消融矩阵（逐个加机制，确认独立贡献）
| 实验 | 配置 | 要回答 |

每组必记：困难任务准确率、平均递归步/题、单题延迟、显存峰值、**直接答错但路由仍选 S1 的比例（选择性风险）**、多次随机种子结果（防偶然提升）。并锁定 参数规模 / 训练数据 / 总预算 可比，否则无法区分提升来自潜在推理、额外训练量还是蒸馏数据质量。

### 11.5 v0.2 落地 + 真实冒烟（2026-10-15 深夜，已实跑）
- **v0.1→v0.2 修正两处真 bug（靠在本机真跑 135M 才暴露）**：
  1. **坐标不一致**：v0.1 用「全模型+norm 末位 hidden」初始化 state 却只让 reason 跑 shared_layers / decode 跑剩余层，空间对不上。v0.2 改为 latent 始终 = backbone 全模型+final norm 的连续表示，直接当虚拟 token 的 embedding 喂回 `model.model(inputs_embeds=latent, past_key_values=cache, use_cache=True)`，与 COCONUT 原论文一致。
  2. **KV 管理**：手工 `tuple/list` 的 past_key_values 在 transformers≥4.40 不被接受（要求 `Cache` 对象）。改用 `DynamicCache`，模型就地追加 KV（思维彼此可见）。另修了 `reason` 返回 `(latent, past)` 的解包顺序写反、`decode` 应是 tokenizer 而非 model 两个低级 bug。
- **实跑验证**：本机装 CPU torch+transformers，用 `models/SmolLM2-135M`（LlamaForCausalLM, 30 层, GQA）真跑 `latent_reasoner.py --smoke` 与 `evaluate_reasoning.py`。结果：**递归/ KV / 完整贪心生成全链路零报错**；135M base 各 steps 准确率均为 0%（**符合预期**——未蒸馏 base + 未训 COCONUT，把 post-norm 隐状态当 embedding 喂回是分布外行为）。eval harness 如实输出「未观察到提升，勿急于加 router/stop」。
- **关键结论**：本机冒烟证明的是**机制链路通，不是研究假设成立**。真实 Gate 2（潜在递归是否提准确率）需要：① `train_distill.py` 先训出 System1 直答基线（阶段 A）→ ② 阶段 B 对潜在递归做训练 → ③ 才能用 `evaluate_reasoning.py` 在 0.3B 蒸馏模型上扫 steps 看提升。缺一不可。
- **下一步（等 0.3B 权重出来，或直接在 135M/200M 上跑阶段 A→B 做最小可行性）**：先用 `train_distill.py` 在 QA 蒸馏数据上训 System1，再补阶段 B 的潜在递归训练脚本（`b4/train_latent.py`），最后跑 Gate 2。router.py / stop_controller.py 仍按 v3 优先级在 Gate 2 通过后再写。

### 11.6 Stage B 落地 + 真实 Gate 2 冒烟/评测（2026-10-15 深夜，已实跑）
- **新增 `b4/train_latent.py`（Stage B 训练骨架）**：`LatentAdapter`（恒等初始化 bottleneck）、`freeze_backbone`、`latent_answer_loss`（末态 + teacher-force 答案算 CE，潜在步不做词表投影）、`train_step`、`gate2_smoke`。已修强模型骨架两处坑：① 显式 `cache_position` + `attention_mask=None`（5.x 增量解码最稳，保 RoPE 连续）；② 手动 `cur_len` 追踪 + 冒烟断言 `cache.get_seq_length()==prompt+steps+answer`。
- **`HybridModel` 加可选 adapter**（递归步里套用），`evaluate_reasoning.py` 加 `--adapter`，打通「训练→加载→评测」全链路；并修 eval 前缀 bug（必须与 `train_distill` 同用 `问题：{q}\n答案：`）。
- **实跑结果（transformers 5.19 / torch 2.14 cpu，模型 SmolLM2-135M）**：
  1. Gate2 实现冒烟 ✅：loss 有限 / grad_norm>0 / adapter 参数真更新 / 缓存长度正确 —— **证明 DynamicCache 反向传播在 5.19 下能穿过缓存把梯度送回 adapter**（强模型最担心的点被证伪）。
  2. Gate2 准确率评测（held-out 60 道算术，steps 0 vs 2+adapter）：直答 5.0%，潜在递归 5.0% —— **无提升**。
  3. ⚠️ 该负结果是**设计性不可结论**：135M 裸权重直答能力本就≈0（5%），潜在递归没有可叠加的 System1，无法测出收益。印证强模型「先证明递归有效再堆路由/停止」纪律，且说明 **Gate 2 必须在已有 System1 能力的底座上测**。
  4. 延迟有用数据：潜在递归仅多 ~140ms（2 个额外前向），相对直答 +3.6% —— latent 开销不随生成 token 数线性膨胀（佐证「内部计算 ≠ 吐 CoT」）。
- **下一步（已在跑/将跑）**：在 135M 上先 Stage A（`train_distill.py` 直答蒸馏）建立 System1 底座 → 再 B1 训 adapter → 再 Gate2，给出「有直答能力时潜在递归是否真提分」的确定性答案；若 135M 仍不显效，则指向「小模型容量不足，需 0.3B+」，届时用真实续训权重测。router.py / stop_controller.py 仍延后。
