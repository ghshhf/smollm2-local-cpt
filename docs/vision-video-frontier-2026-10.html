一、当前状态：模型没有视觉

主线 SmolLM2 续预训练链（0.1B → 0.5B）是纯语言模型，无视觉编码器，不能识图。 注意 docs/vision-0.5B-fusion.md 里的 "vision" 是愿景不是视觉。

二、加视觉：可行，且有跟我们同源的现成蓝本

最关键的发现

VisionPsy-Nano（Tether/QVAC，2026-07-29 开源，Apache 2.0）：460M 参数 VLM = SigLIP2 视觉编码器 + 360M 参数的 SmolLM2 语言主干（nanoVLM 框架）。
在 17 个基准上取得 sub-0.5B 类最高归一化分 62.3，超过 Liquid AI LFM2.5-VL-450M（59.6）与 HF SmolVLM2-500M（52.5）；视觉感知 +4.6%、视觉推理 +7.4%。
它用的语言主干就是 SmolLM2 —— 和我们的基座是同一个。

工程范式（2026 主流，也是我们要走的路）

ViT/SigLIP 编码器 + 2 层 MLP 投影层（仅约 21M 参数）+ LLM 解码器，early fusion：视觉 token 拼进文本 token 流。

三阶段训练：① 冻 ViT 与 LLM，只训 projector（对齐）→ ② 训 ViT + projector → ③ 全参数指令微调。
差速学习率：视觉编码器低 LR、LLM 中、projector 高 —— 防灾难性遗忘。这与我们的保函数扩容思路同构：语言主干能力不损失
关键约束数据
视觉 token 爆炸336px 图 = 576 token；AnyRes 平铺按 tile 数倍增。Flash 版压到 64 token 是最省的做法
数据质量 > 数量LLaVA-1.5 用 665K 高质量指令样本胜过数百万噪声样本

三、Opus 5.5「代码编辑视频」的真实机制

Opus 5.5 不生成像素，它生成代码。Anthropic 官方能力里根本没有"视频"这一项——视频是代码能力 + 长程规划的副产品。
流水线机制适用
① 单文件 HTML一个 HTML：舞台 + 场景时间轴 + CSS keyframes / Web Animations API / canvas 渲染循环，浏览器直接播动效、字体排版、15 秒 showreel
② 渲染框架Remotion（React 组件当时间轴 → 确定性 MP4）、HyperFrames、p5.js、Three.js、Manim；headless Chrome 逐帧捕获 → FFmpeg 编码可复现、可版本管理
③ 多模型编排Claude 当导演写分镜与 prompt，调 Seedance / 可灵等视频模型，再用 FFmpeg 缝合需要写实人物时

为什么这套强：「因为输出是代码，修改就是编辑」——把第三场缩短两秒 是一行改动 + 重新渲染，不是回到时间轴手动拖。整个项目可进 Git 做版本管理。

质量来自 harness，不是魔法 prompt：风格指南（字体/配色/转场）、组件规格、分镜计划、以及让模型逐帧分析参考片提取调色板/字体/镜头时长/运镜，再用这套视觉语法构建新片。

局限：画不好活物（人脸近看是粗糙几何）、易过曝、成本高（API $4/M 输入、$20/M 输出；一支 3 分钟旁白短片用掉周额度约 7%）、需要 Node + Chrome + FFmpeg 执行环境。

三条最有价值的结论：
  • 瓶颈不是"会不会用工具"，是审美与手艺。72.9% 的失败只败在质量测试——agent 靠静态帧和转录稿"感知"素材，只检查渲染的技术缺陷（黑场/静音/格式），不懂叙事匠心。
  • 代码路线 >> GUI 路线。Timeline-Bench 里 computer-use（用鼠标操作 DaVinci）相对代码路线劣化 16.4 个百分点，p<0.001（2/53 vs 12）。这和我们"脚本断言 > 人肉目检"的验收哲学同构
  • harness 的边际收益有限。给通用剪辑指导把 21.4% 提到 26.8%，但人类盲评只 +0.6pp（不显著）；换 harness 也无统计显著差异。

五、落到我们的两条线

A 线 — 模型本体（加视觉）

项建议
架构SigLIP2 编码器 + 2 层 MLP 投影（~21M）+ 现有 SmolLM2 主干，语言主干冻结或低 LR → 语言能力不损失（保函数）
训练三阶段：对齐（只训 projector）→ 训 ViT+projector → 全参数指令微调；差速 LR
Token 预算走 Flash 思路压到 64 视觉 token，否则端侧 KV-cache 吃不消
数据重质量不重量（参照 LLaVA-1.5 的 665K 高质量样本思路）
参数抉择（待拍板）① 语言 500M + 视觉 ~100M = 总量 ~600M（语言能力优先）
② 语言 360M + 视觉 100M = 460M（对齐 VisionPsy-Nano，端侧友好）
宪法约束E-7：个人照片/视频绝不进被训练参数，只进可寻址可删除的记忆层

B 线 — 能力外置（学剪辑，重点）

剪辑能力不进权重。按我们的哲学（智能 = 借用工具 + 极简验证），模型只需四件事：
① 理解意图 → ② 生成 Remotion / FFmpeg / Manim 代码 → ③ 调工具执行 → ④ 脚本验收（时长、分辨率、黑场、静音、字幕对齐、接缝帧）。
  • 训练数据：代码-视频对（Remotion 组件、FFmpeg 命令、Manim 脚本）+ 分镜规划 + 参考片逐帧分析文本。
  • Verifier 是关键：Timeline-Bench 证明瓶颈在质量而非合规 → 用看门狗 + 视觉验收 + 共享黑板多模型评委（zen-gate 模型池）来补"审美"这一环，人只做最终目检。这正是我们 B 线已有的基础设施。
  • 识图是剪辑的前提：加视觉后 agent 才不用"只靠静态帧 + 转录稿"——Timeline-Bench 的失败根因恰在这里。

六、待拍板

  1. 加不加视觉：0.5B 之后加，还是 0.5B 就带？
  2. 参数分配：600M（语言优先）还是 460M（对齐 VisionPsy-Nano，端侧友好）？
  3. 剪辑走哪层：纯 B 线（工具 + harness，零训练成本）还是给模型补代码-视频对的微调？
