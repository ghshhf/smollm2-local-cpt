一、为什么这一步是纯赚

查 chain_v2.sh 才发现一个关键事实：每档的 budget 是步数阈值而不是语料量——

  • R7：done 6800→8300 ｜ R8：8300→9800 ｜ R9：9800→11300 ｜ R10：11300→12800，每档 1500 步
  • 1500 步 × 4096 token/步 = 614 万 token 硬需求
  • 而原语料每档约 2.2 亿 token ⇒ 过剩 36 倍

也就是说：训练器本来就只吃掉语料前面随机的一小截。既然如此， 与其让它吃"随机的前 3%"，不如让它吃"按信息密度挑出来的前 3%"——这就是数据蒸馏。 附带好处：tokenize 缓存从 300MB 级降到 20–40MB 级，每档开训更快。

四、处理流程

Pass 0 · 硬过滤（纯增益，只去污染不去内容）

  • 指令模板残留：你是一位小说写手、<|im_start|>、Human:/Assistant:、[INST]
  • 续写流水账痕迹：继续写下去：、续写：、接上文： —— 实测抓出 7,139 条
  • 网页 / 广告噪声：扫码关注、公众号 ID、HTML 标签、<span style=font-family:、URL
  • 许可证样板：Project Gutenberg 头尾、mojibake、控制字符、非中文

Pass 1 · 块级去重

200 字块做 sha1。整篇 >60% 的块已见过 ⇒ 判为转载，整篇丢弃； 否则只保留独有块——去水但不连独有内容一起倒掉。

Pass 2 · 信息密度打分（纯统计，不用模型）

汉字占比 .26 ＋ 唯一字率 .22 ＋ 噪声率 .16 ＋ 段落结构 .14 ＋ 句末完整 .10 ＋ 长度贴合 .06 ＋ 刷屏检测 .06。

为什么不用模型打分：用自家训的小模型给语料打分会形成自举偏见，把已有偏差越洗越深。 整套打分只用统计量，不引入任何外部判断。

Pass 3 · 蒸馏取 top N ＋ 多样性配额

按分数降序累计 token 到预算为止；同一"书名/来源"最多入选 N 条，防止被几本书灌满。

Pass 4 · 报告留痕

每档的条数、字节、丢弃原因分布、来源覆盖数全部落盘，可回溯。

五、首轮跑完发现的三个真问题（已修）

第一轮产出的数字很好看，但抽样一看露出三个问题——数字好看不等于语料合格，这是必须过的一关。

问题 1novels 多样性塌了

1,887 条只覆盖 186 本书，前三本占 54%（《暗黑之神》441 条、《傲剑蛮荒》417 条、《奥比岛》161 条）。 按分数排序会把同一本书的高分章节连成一串全选进来。

修复：加多样性配额（每书 ≤30 条）。重跑后覆盖 186 → 433，主动跳过 3,636 条超额条目。

问题 2knowledge 被写手续写流水账灌满

抽样出现大量 继续写下去：王杰觉得还是最普通的姿势最容易达到… 这类片段。 这是写手流水线产物的指令痕迹，属于数据集污染。

与宪法原则的边界：删的是"续写指令痕迹"这一结构污染， 不是按主题删成人内容——用户 2026-10-14 定的"不删成人内容、退化靠加覆盖不靠审查"原则原样保留。 另外对 knowledge 档加了 0.35 的叙事体惩罚（按引号密度判断体例而非内容），让百科型压过小说体。

问题 3ancient 有 HTML 残留漏网

来源 Top1 是 <span style= font-family:（连写形式），原正则只匹配了 <div 等标准写法。

修复：正则补上 </?span、font-family、font-size 等。
